| D-011 | 2026-10-09 | MMR: the public leaderboard is the guide. Closes P-008. | User's decision; Blizzard's website terms grant a "personal use only" license and exclude commercial use and downloading except page caching. |
| D-013 | 2026-10-09 | Leaderboard client strategy: full sweep (all pages) at most once a day per region and mode; in between, a targeted search of up to 5 pages around the last known rank, which only gives a rating if the last full sweep is ≤ 7 days old; if it can't be refreshed, the last state is shown with its time. See `docs/research/leaderboard-client.md`. |
| D-014 | 2026-10-09 | Desktop app with **Tauri 2**: logic (parser, log following, leaderboard, storage) in Rust and UI in HTML/TypeScript. Plan B, WPF, only if the overlay fails later. | D-015 | 2026-10-09 | Local history in a JSONL file (`%APPDATA%\TavernLedger\games.jsonl`): one record per game keyed by session + game number; if a game is saved more than once, the last one wins. No database until the stats (T-102) ask for one. | Simple, no dependencies, easy to export and delete (GDPR) and robust: a line cut by an abrupt shutdown is counted and reported, and doesn't break the rest. | D-016 | 2026-10-09 | Single instance: the app and `tavern-watch` take a system lock on `%APPDATA%\TavernLedger\games.lock` before writing the history; if it is taken, the second process says so and doesn't write (the app shows the history read-only). No `tauri-plugin-single-instance` for now. | Claude's decision (the user asked for more autonomy): standard library (`File::try_lock`), no new dependencies; the system releases the lock if the process dies, so no orphan locks remain, and it also covers `tavern-watch`, which the plugin doesn't. What is lost: focusing the window that is already open. |
| D-017 | 2026-10-09 | Hero names come from `Power.log` itself (`[entityName=… cardId=…]` references), in the client language; no external card dataset. A hero with no name in the log shows with its id. | It is exactly what the player sees on screen (D-004) and brings no third-party data into the repo: the HearthstoneJSON JSONs are "Copyright © Blizzard Entertainment - All Rights Reserved" and `hsdata` has no license. Player entities (BattleTag) have no `cardId` and never get in; the report only stores hero names. |
| D-018 | 2026-10-09 | The app lives in the tray: closing the window hides it and it keeps reading the log; "Quit" in the tray menu closes it. Start with Windows through `tauri-plugin-autostart` 2.5.1 (entry in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, with `--minimized`), **off by default** and only turned on by the user from the menu. The app's web page can't turn it on (its permissions don't include the plugin). If the app path has spaces, the option shows as off: `auto-launch` 0.5 writes the path without quotes. | User's OK for the new dependencies (Tauri `tray-icon` feature and the official plugin, MIT or Apache-2.0). If the window were closed completely, games played afterwards wouldn't be saved. |
| D-019 | 2026-10-09 | Per-hero stats group skins by dropping a trailing `_SKIN_<letters and digits>` from the card id, and nothing else. The hero's name is the base id's name if any game in the history prints it, else the first named skin. | Claude's decision (T-102), from the real history: every `_SKIN_` group names the same hero (e.g. `BG20_HERO_202`, `_SKIN_B4` and `_SKIN_C` are all Nguyen; one skin id is printed with both names). Ids that only share a number (`BG20_HERO_102` and `TB_BaconShop_HERO_102_SKIN_G`) or have other suffixes (`…pe`) stay apart: merging them would need a mapping we do not have (D-017). |
| D-020 | 2026-10-09 | Web stack: **static Astro site + Supabase** (Postgres, auth, storage) in an EU region (Frankfurt). Each game is stored gzipped in Supabase Storage with a summary row in Postgres; the desktop app signs in through the browser (authorization code + PKCE, loopback redirect) and uploads with `PUT` keyed by session + game index. No Battle.net login: email login, Discord or GitHub optional. Plan B: all on Cloudflare (Workers, D1 with EU jurisdiction, R2, Better Auth). Closes P-003. | User's choice after T-103. Ready-made auth for a one-person project, open source (Apache-2.0) and self-hostable, `pg_dump` export, EU region and a DPA on the free plan. Vercel Hobby bans commercial use and has no DPA. Blizzard's Developer API terms forbid apps with paid features (2(b)) and keeping API data over 30 days (2(s)), so Battle.net login is out. Known costs: the free project pauses after a week idle and has no backups, so until Pro ($25/month) weekly dumps run from the developer's machine, and the project moves to Pro before the first public users unless real traffic keeps it awake; no keep-alive pings. See `docs/research/web-stack.md`. |
| D-021 | 2026-10-09 | Backend layout (T-104a): clients only read; game rows and files are written by the service role only. Export is one SQL function (`export_my_data`, the signed-in user only). Deletion is the `delete-account` Edge Function: files through the Storage API, then rows (`delete_user_data`, which refuses while files remain), then the auth user, then its audit entries (`delete_user_auth_events`, including the one the auth deletion writes). Weekly backups from the developer's machine with `tools/backup_supabase.ps1`, kept 35 days. Supabase CLI 2.118.0 pinned as an npm dev dependency; database tests (pgTAP) and the end-to-end test run against the local stack, not in CI. | Claude's decision with the user's OK for the CLI and Docker (session 012). Deleting `storage.objects` rows in SQL leaves the file bytes behind, so files need the Storage API; audit entries have no foreign key to the user and outlive a plain auth deletion. The local stack needs Docker images (about 3 GB), too slow for the 5-minute CI job (D-008). The hosted project waits for the user (account, terms, DPA). |
| D-022 | 2026-10-09 | Reconnect/unplug (dropping the game's connection to skip combat animations) exists only as a **dev tool**: under `tools/dev/`, never in the app, the installer, releases or user docs; run by hand on the user's own account, with admin rights, knowing it can carry account risk. Games played with it are marked so they never become fixtures or count as normal games. Building it is task T-D01 and needs the user's OK when it starts. | User's decision after the GitHub survey ([github-landscape.md](../research/github-landscape.md)): it saves time when collecting test games, but it changes how the client behaves on the network, which the product rules out (D-004). Other tools that ship it to users are the risky category; HDT marks reconnected games as unreliable. |
| D-023 | 2026-10-09 | Website (T-104c): static Astro site in `web/` with its own lockfile; Astro 7.3.5 and `@supabase/supabase-js` 2.117.2 pinned exactly, picking releases at least two weeks old, and npm install scripts off. Nothing is inlined into the pages, so the Content-Security-Policy allows scripts and styles from the site only and connections to the Supabase project only; data reaches the page through `textContent` only. Session in supabase-js's default storage, PKCE flow. Public profile at `/profile/?id=<user id>`: a private, missing or malformed id gives the same "not found". Export: `export_my_data()` plus each game file as base64 of its gzip bytes, in one JSON file (no zip dependency). `delete-account` accepts browser requests only from `SITE_ORIGINS` (requests with no `Origin` header still need a valid token) and only when both the account's last sign-in and this session's own sign-in (the access token's `amr` time) are under 10 minutes old, with a minute of clock tolerance; otherwise the site asks for the password again. The account page says plainly that a public profile makes every uploaded game readable in full by anyone, as the T-104a schema allows (the F2 viewer needs it). | Claude's decision (session 013). Fewest moving parts that meet the brief: no test runner or UI kit (Node's own test runner), no custom session storage. A two-week-old release has had time for a bad publish to be pulled. Known limits: the local gateway answers preflights itself with `Access-Control-Allow-Origin: *`, so locally the function's 403 is what enforces the origin, and whether the hosted gateway passes the function's own CORS headers through is **unverified**. |
| D-024 | 2026-10-09 | The parser version is saved per record, outside the report: `parser: {version, revision}` where `version` is the `bg-parser` crate version and `revision` is `PARSER_REVISION`, bumped by hand whenever parsing changes. Records without it are "unknown version", not errors. `tavern-watch --reparse` re-reads a session only if its logs hold every game the history has for it; otherwise nothing of that session is overwritten and the games are listed. A re-read that is worse than a saved `ok` game (cut-short log) is listed, not saved; games not already in the history are not added. | Claude's decision (T-107). Outside the report so a new parser version alone never makes a game "changed". A session whose logs lost their first part (the game rotates `Power_old.log`) would number its games from 1 again, and writing those reports over the old ones would put games under the wrong number; D-015's last-record-wins would make that permanent. |
| D-026 | 2026-10-09 | Problem-report bundle (T-110): the file is built and checked in Rust (`tracker::report_bundle`) from an allowed set of fields; a field outside it, a BattleTag-shaped or account-id-shaped text, or a text over 2000 characters makes the app refuse the whole bundle, never cut the field out. The window shows the file as the app built it and saving rebuilds it, never trusting window text; it goes to the Downloads folder (`%USERPROFILE%\Downloads`), never over an existing file, with no folder picker. Source labels (T-109) are data from Rust (`tracker::provenance`), shown with a mark for every source but the log. | Claude's decision (session 017). A picker needs `tauri-plugin-dialog`, a new dependency that is the user's call; Downloads is the place the user can find the file, and the file is small and for sending by hand. Refusing whole is safer than stripping: a stripped field could leave the rest of a name in another place. A one-word name with no `#` fits a plain id, so the check is a second line behind the parser (which keeps names out, D-017), not a name detector. The check can refuse a legitimate game (a hero or card text with `#` and digits is not expected); the message says which field, and nothing leaves the app. |
| D-027 | 2026-10-09 | Privacy and terms (T-104b): no analytics of any kind on the site; minimum age 16 to create an account; the controller publishes a dedicated project email address, never the user's personal one (name, country and address still to be filled in). The policy and terms live in `docs/legal/` and the site renders those same files, so they cannot drift. The outbound email sender for auth emails stays **open**: the user first picked Brevo, then (relayed by the hub) chose to decide once the domain is bought, planning Cloudflare's email features; Cloudflare Email Routing only forwards incoming mail, so a separate outbound sender with a DPA is still needed. | User's decisions (session 018), except the single-source pages (Claude's). No analytics means no cookie banner and one processor fewer; 16 is the GDPR default age of digital consent where a country sets none lower. |
| D-028 | 2026-10-09 | Combat results (T-202, T-203) are **worked out from health**, never read: the log has no winner. The parser keeps every lobby hero's health (health + armor - damage) before the first combat and after each combat (`start_health`, `Round::health_after`, Rust-only, parser revision 2). A combat is *lost* if only our side lost health, *won* if only the opponent's did, *tie* if neither did, and *unknown* if both did, a side gained health or was already out (a ghost), or a number is missing; all but unknown are labelled inferred. In Duos a round is one result for our team against the opposing team (both fights together), since a team shares one health pool; two teammates with different numbers give unknown. Opponents are a hero and a seat of that game only. | Claude's decision (session 019). Needs no new dependency and stays inside the red line (D-004, D-012): only what the player's own screen showed. Known limits: a tie may hide a hit prevented by a hero power; round 1 of Duos is unknown because the pool forms during it; games saved by revision 1 stay unknown until re-read. |
| D-029 | 2026-10-09 | Lobby tribes entered by hand (T-303) are saved in their own file, `lobby_tribes.json`, next to the history, keyed by session and game number, **never inside the parser's report** (like `parser` in D-024), so re-reading a game keeps them. The user picks exactly five distinct tribes from a fixed list (the log's `CARDRACE` names: Aberration, Beast, Demon, Dragon, Elemental, Mechanical, Murloc, Naga, Pirate, Quilboar, Undead); no free text. An entry made during a game goes to that game; with none in progress it waits for the next game that starts. They are always shown as *entered by you*, next to the tavern tribes and never merged or used to correct them; the stats count them in their own table. Only the window that holds the history lock writes the file. | Claude's decision (session 020). No new dependency; inside the red line (D-004, D-006): the app reads nothing from the game's screen or memory, the user types what they see. The fixed list is a constant: when Blizzard adds a tribe it has to be added by hand (Draenei was not seen in the user's 23 real games, so it is not in the list). Known limit: a game cut off without a COMPLETE stays "in progress" until the next one starts, so an entry waiting then goes to it; the user can move it from the history. |
| D-030 | 2026-10-09 | Hosting and mail (T-104c deploy): the site is served by **Cloudflare Pages through Git integration** (the Pages GitHub app on `KBroneZ/tavern-ledger` only; root `web/`, production branch `main`, preview deployments off, build command runs the unit tests, the build and the checks on the built files) at `tavernledger.net`, with `www` sent to the apex by a 301 (proxied placeholder record + Bulk Redirect). Until the hosted Supabase project is wired in, the site is built with **accounts closed**: no Supabase settings, no form, no script, CSP allowing no script, form or connection. Security headers come from the build (`dist/_headers`), HSTS starting at one day. Cloudflare features that inject scripts or prefetch (Web Analytics, Email Address Obfuscation, Bot Fight Mode, Rocket Loader, Speed Brain) stay off. Contact mail: **Cloudflare Email Routing** forwards `contact@` and `privacy@tavernledger.net` to the user's mailbox, catch-all off, DMARC `p=reject` while nothing sends. Outbound sender for Supabase's auth emails: **Cloudflare Email Sending** (user's choice), set up by session 022, which then owns `_dmarc` and merges into the one apex SPF record. Closes the sender question left open in D-027. | Git integration needs no API token in GitHub and no new dependency; the repo is public, so the app's read access exposes nothing new. Accounts closed means nothing on the site can break or call a backend that does not exist. Sender: Claude recommended Brevo (free, plain SMTP on Supabase's documented port, EU, not a beta); the user chose Cloudflare for one provider and dashboard, accepting Workers Paid ($5/month) and a beta SMTP on port 465. See `docs/research/deploy.md`. |
