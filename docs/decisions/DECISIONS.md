| D-021 | 2026-10-09 | Backend layout (T-104a): clients only read; game rows and files are written by the service role only. Export is one SQL function (`export_my_data`, the signed-in user only). | D-022 | 2026-10-09 | Reconnect/unplug (dropping the game's connection to skip combat animations) exists only as a **dev tool**: under `tools/dev/`, never in the app, the installer, releases or user docs; run by hand on the user's own account, with admin rights, knowing it can carry account risk. | D-023 | 2026-10-09 | Website (T-104c): static Astro site in `web/` with its own lockfile; Astro 7.3.5 and `@supabase/supabase-js` 2.117.2 pinned exactly, picking releases at least two weeks old, and npm install scripts off. Nothing is inlined into the pages, so the Content-Security-Policy allows scripts and styles from the site only and connections to the Supabase project only; data reaches the page through `textContent` only. The account page says plainly that a public profile makes every uploaded game readable in full by anyone, as the T-104a schema allows (the F2 viewer needs it). | Claude's decision (session 013). | D-024 | 2026-10-09 | The parser version is saved per record, outside the report: `parser: {version, revision}` where `version` is the `bg-parser` crate version and `revision` is `PARSER_REVISION`, bumped by hand whenever parsing changes. Records without it are "unknown version", not errors. `tavern-watch --reparse` re-reads a session only if its logs hold every game the history has for it; otherwise nothing of that session is overwritten and the games are listed. A re-read that is worse than a saved `ok` game (cut-short log) is listed, not saved; games not already in the history are not added. | Claude's decision (T-107). Outside the report so a new parser version alone never makes a game "changed". A session whose logs lost their first part (the game rotates `Power_old.log`) would number its games from 1 again, and writing those reports over the old ones would put games under the wrong number; D-015's last-record-wins would make that permanent. |
| D-025 | 2026-10-09 | Desktop upload (T-104d). **Sign-in:** the app asks Supabase for a one-time email link with a PKCE challenge (`create_user: false`: accounts are made on the website) and listens on `127.0.0.1` on a port the system picks, at `/desktop-callback/<random state>`; the link opens in the system browser and lands there with `?code=`, which the app trades with its verifier. Supabase Auth accepts any IP-loopback redirect on any port without an allow-list entry (checked on GoTrue v2.197.0). The app never asks for a password. **Tokens:** the refresh token in Windows Credential Manager (one credential per data folder), the access token only in memory, a rotated token saved before it is used; sign-out revokes the session on the server, removes the credential and turns upload off. **Upload:** `PUT /functions/v1/upload-game/v1/games/<session>/<index>` with `Content-Type: application/gzip` (not `Content-Encoding`, so no proxy inflates it); the function accepts only compact JSON with no repeated keys and checks the record field by field (only the report's fields, no BattleTag-shaped string, hero names only for heroes the report shows, Solo and Duos only), stores the file re-compressed from the checked bytes (a gzip header could carry a name), then the row; quotas in SQL (`upload_begin`): 600 an hour, 5,000 a day, 10,000 games and 50 MiB per user, 30 refused tokens per hashed IP in 10 minutes (a blocked IP still serves a valid token). A daily `sweep` function removes files with no row, audit entries of deleted accounts and expired counters. **Queue:** `uploads.jsonl` next to the history marks each game by account and SHA-256 of the exact JSON sent; 400/409/413 with one of the function's own codes mark that game refused (sent again only if its record changes), 403 and any other 4xx stop and say why, 429 waits for `Retry-After`, network errors and 5xx back off 2 s to 15 min with jitter. Off until the user signs in and turns it on; signing in never turns it on. **Server:** `server.json` in the data folder until the hosted project exists; only https, or http on `127.0.0.1`, and only a public key. New dependencies: reqwest's `native-tls` feature (Windows TLS), with the user's OK in session 016. | Claude's decision within the design of T-103 (`web-stack.md`, "Upload design"). A magic link needs no OAuth provider account and works with the email sign-in the website already has; PKCE makes a leaked code useless without the app's verifier, and the random state in the path stops an old or forged link from finishing a sign-in. Re-compressing on the server means what is public is exactly what was checked. Known limits: uploads in flight can pass the quota by a few games; two PCs uploading the same game in the same second can leave the file one revision behind the row; the IP is the platform's client-IP header, else the first `X-Forwarded-For` entry, which only matters for refused tokens and is **unverified** on the hosted gateway. |
