# Decisions

## Made

| ID | Date | Decision | Reason |
|----|------|----------|--------|
| D-001 | 2026-10-08 | Own repo, separate from StartAICareer. | Don't mix with the HQ's CI, PRs or Actions minutes; it is a personal project. |
| D-002 | 2026-10-08 | The desktop app is open source (MIT). Premium lives on the server. | User trust and free or cheap code signing (SignPath Foundation, Certum Open Source). |
| D-003 | 2026-10-08 | Model: everything personal is free (history, stats per hero, MMR, opponents, replays with a limit). Optional paid extras. No ads. | Personal, non-profit project; stand apart from Firestone Premium and Tier7. |
| D-004 | 2026-10-08 | MVP with local logs only: no memory reading, no injection, no automation. | Blizzard EULA and ban risk for users. See `docs/research/feasibility.md`. |
| D-005 | 2026-10-08 | MMR from Blizzard's public leaderboard; outside the leaderboard, "no data" (never an invented value). | The leaderboard only covers the top (~8000 MMR, about 4300 accounts in EU); see research. |
| D-006 | 2026-10-08 | **No injection and no client modification, ever** (BepInEx, DLLs, patches to game files). Nomi's "minion dance" is discarded. Closes P-004. | User's decision: nothing that goes against Blizzard's rules. |
| D-007 | 2026-10-08 | Name: **Tavern Ledger** (repo `tavern-ledger`). Closes P-001. | User's choice. No evident tracker or brand with that name; GitHub and `.gg`/`.app` domains free. See `docs/research/names.md`. |
| D-008 | 2026-10-08 | Public repo on GitHub under the KBroneZ account. Changes to `main` only by PR with green CI. | User's choice; Actions are free on public repos. Still, CI runs in a single job, with `concurrency` (cancels old runs) and a 5 min timeout, to avoid spending minutes if the repo goes private. |
| D-009 | 2026-10-08 | Python dependencies pinned with version and hash in `requirements.txt` (pure wheels only, `pip --require-hashes`). First ones: `hslog` 1.20.0 and `hearthstone` 9.21.1 (MIT). | Approved by the user in session 002. Reproducible builds and protection against tampered packages; origin and license in `PROVENANCE.md`. |
| D-010 | 2026-10-08 | The parser reads each game with a fresh parser and only shows boards that enter play; combats the log doesn't replay come out as "not visible". | `hslog` fails with several Duos games in one log; the `SETASIDE` copies of hidden combats are not seen on screen (rule 3). See `docs/research/parser-hslog.md`. |
| D-011 | 2026-10-09 | MMR: the public leaderboard is the guide. If the player appears, their rating is shown; if they don't appear after checking the whole leaderboard of their region, mode and season, "below the cutoff" is shown (today, < 8000), never a number. If the query fails or is left half done, "unknown"; if their name appears repeated, "ambiguous". The cutoff is taken from the rating of the last row, not fixed at 8000. Closes P-007. | User's decision: few people play, so being outside the top already says something useful. It is a bound with public data, not an invented value (D-005). No local log carries the MMR (T-004). See `docs/research/mmr-sources.md`. |
| D-012 | 2026-10-09 | The leaderboard MMR is a free feature (D-003). The query comes only from each user's desktop app, for their own row, on request or after a game, with cache and the minimum of requests; no crawling from a server, no storing other players' rows and never in paid extras. The concrete design to spend few requests is up to Claude. Closes P-008. | User's decision; Blizzard's website terms grant a "personal use only" license and exclude commercial use and downloading except page caching. |
| D-013 | 2026-10-09 | Leaderboard client strategy: full sweep (all pages) at most once a day per region and mode; in between, a targeted search of up to 5 pages around the last known rank, which only gives a rating if the last full sweep is ≤ 7 days old; if it can't be refreshed, the last state is shown with its time. Gzip yes, `If-None-Match` no. 1.5 s between requests, 15 s timeout, 2 retries, 60 targeted requests a day, 1 h pause after a 403 or 429. | T-006 measurements: gzip cuts each page from 308 to 17 KB; the `ETag` changes on every response; near the cutoff there are 10–30 players per MMR point, so one game moves dozens of pages and "below the cutoff" can only be claimed after checking all of them (D-011). See `docs/research/leaderboard-client.md`. |
| D-014 | 2026-10-09 | Desktop app with **Tauri 2**: logic (parser, log following, leaderboard, storage) in Rust and UI in HTML/TypeScript. Plan B, WPF, only if the overlay fails later. Closes P-002. | User's decision after T-005: small installer (WebView2 ships with Windows), official signed updater, UI reusable on the web and overlay checked on top of fullscreen Hearthstone. See `docs/research/desktop-stack.md`. |
| D-015 | 2026-10-09 | Local history in a JSONL file (`%APPDATA%\TavernLedger\games.jsonl`): one record per game keyed by session + game number; if a game is saved more than once, the last one wins. No database until the stats (T-102) ask for one. | Simple, no dependencies, easy to export and delete (GDPR) and robust: a line cut by an abrupt shutdown is counted and reported, and doesn't break the rest. See T-101 in the plan. |
| D-016 | 2026-10-09 | Single instance: the app and `tavern-watch` take a system lock on `%APPDATA%\TavernLedger\games.lock` before writing the history; if it is taken, the second process says so and doesn't write (the app shows the history read-only). No `tauri-plugin-single-instance` for now. | Claude's decision (the user asked for more autonomy): standard library (`File::try_lock`), no new dependencies; the system releases the lock if the process dies, so no orphan locks remain, and it also covers `tavern-watch`, which the plugin doesn't. What is lost: focusing the window that is already open. |
| D-017 | 2026-10-09 | Hero names come from `Power.log` itself (`[entityName=… cardId=…]` references), in the client language; no external card dataset. A hero with no name in the log shows with its id. | It is exactly what the player sees on screen (D-004) and brings no third-party data into the repo: the HearthstoneJSON JSONs are "Copyright © Blizzard Entertainment - All Rights Reserved" and `hsdata` has no license. Player entities (BattleTag) have no `cardId` and never get in; the report only stores hero names. |
| D-018 | 2026-10-09 | The app lives in the tray: closing the window hides it and it keeps reading the log; "Quit" in the tray menu closes it. Start with Windows through `tauri-plugin-autostart` 2.5.1 (entry in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, with `--minimized`), **off by default** and only turned on by the user from the menu. The app's web page can't turn it on (its permissions don't include the plugin). If the app path has spaces, the option shows as off: `auto-launch` 0.5 writes the path without quotes. | User's OK for the new dependencies (Tauri `tray-icon` feature and the official plugin, MIT or Apache-2.0). If the window were closed completely, games played afterwards wouldn't be saved. |
| D-019 | 2026-10-09 | Per-hero stats group skins by dropping a trailing `_SKIN_<letters and digits>` from the card id, and nothing else. The hero's name is the base id's name if any game in the history prints it, else the first named skin. | Claude's decision (T-102), from the real history: every `_SKIN_` group names the same hero (e.g. `BG20_HERO_202`, `_SKIN_B4` and `_SKIN_C` are all Nguyen; one skin id is printed with both names). Ids that only share a number (`BG20_HERO_102` and `TB_BaconShop_HERO_102_SKIN_G`) or have other suffixes (`…pe`) stay apart: merging them would need a mapping we do not have (D-017). |
| D-020 | 2026-10-09 | Web stack: **static Astro site + Supabase** (Postgres, auth, storage) in an EU region (Frankfurt). Each game is stored gzipped in Supabase Storage with a summary row in Postgres; the desktop app signs in through the browser (authorization code + PKCE, loopback redirect) and uploads with `PUT` keyed by session + game index. No Battle.net login: email login, Discord or GitHub optional. Plan B: all on Cloudflare (Workers, D1 with EU jurisdiction, R2, Better Auth). Closes P-003. | User's choice after T-103. Ready-made auth for a one-person project, open source (Apache-2.0) and self-hostable, `pg_dump` export, EU region and a DPA on the free plan. Vercel Hobby bans commercial use and has no DPA. Blizzard's Developer API terms forbid apps with paid features (2(b)) and keeping API data over 30 days (2(s)), so Battle.net login is out. Known costs: the free project pauses after a week idle and has no backups, so until Pro ($25/month) weekly dumps run from the developer's machine, and the project moves to Pro before the first public users unless real traffic keeps it awake; no keep-alive pings. See `docs/research/web-stack.md`. |
| D-021 | 2026-10-09 | Backend layout (T-104a): clients only read; game rows and files are written by the service role only. Export is one SQL function (`export_my_data`, the signed-in user only). Deletion is the `delete-account` Edge Function: files through the Storage API, then rows (`delete_user_data`, which refuses while files remain), then the auth user, then its audit entries (`delete_user_auth_events`, including the one the auth deletion writes). Weekly backups from the developer's machine with `tools/backup_supabase.ps1`, kept 35 days. Supabase CLI 2.118.0 pinned as an npm dev dependency; database tests (pgTAP) and the end-to-end test run against the local stack, not in CI. | Claude's decision with the user's OK for the CLI and Docker (session 012). Deleting `storage.objects` rows in SQL leaves the file bytes behind, so files need the Storage API; audit entries have no foreign key to the user and outlive a plain auth deletion. The local stack needs Docker images (about 3 GB), too slow for the 5-minute CI job (D-008). The hosted project waits for the user (account, terms, DPA). |
| D-022 | 2026-10-09 | Reconnect/unplug (dropping the game's connection to skip combat animations) exists only as a **dev tool**: under `tools/dev/`, never in the app, the installer, releases or user docs; run by hand on the user's own account, with admin rights, knowing it can carry account risk. Games played with it are marked so they never become fixtures or count as normal games. Building it is task T-D01 and needs the user's OK when it starts. | User's decision after the GitHub survey ([github-landscape.md](../research/github-landscape.md)): it saves time when collecting test games, but it changes how the client behaves on the network, which the product rules out (D-004). Other tools that ship it to users are the risky category; HDT marks reconnected games as unreliable. |
