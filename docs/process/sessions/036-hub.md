## How things work now (lessons from round 2)

- **Launching:** `switch-account` skill, script `open-session.ps1`: `-Account A -Model … -Effort … -Title "NNN <name>" -Worktree NNN-slug -InitialPrompt "Read prompts/sessions/NNN-slug.md and act on it. Do not stop. I write in Spanish, you answer in English."`. The prompt file must be on `origin/main` first.
- **Account B is blocked** (its organization disabled Claude subscription access for Claude Code). Use **account A only** until the user says otherwise. A has a 5-hour cap (80%): if the script exits 3, wait for the reset it prints.
- **`gh` is logged in only in the hub** (`GH_TOKEN`; never print it). Task sessions push their branch and message the hub (`SendMessage`, names from `ListAgents` with their `[ref]`) with branch, PR title and body. The hub checks the diff (shared docs only the session's rows, LF line endings, `git merge-tree` clean, nothing secret or personal), opens the PR, waits for CI (`gh pr checks --watch`), merges with `gh pr merge <n> --squash --delete-branch` (the local-branch delete fails while the worktree exists: ignore it), pulls `main`, and tells the session it is finished.
- **Every task prompt** must say: work only in your worktree; keep changed text files LF (a CRLF file rewrites the whole file and conflicts with others); `gh` is not logged in, hand the PR to the hub; never stop or restart the user's desktop app.
- **Tier check before merging:** anything that changes what is uploaded, network code, auth or user data is R2 and needs `/security-review` as well as `/code-review`. Real-log fixtures going public: re-scan them yourself (no `#digits`, no `entityName`, no non-ASCII, no 9+ digit numbers, `GameAccountId` only placeholders, `PlayerName` only `Player1`/`OpponentN`).
- **Uploads:** `supabase/functions/upload-game/report_keys.json` and `validate.ts` must accept every key the parser writes; `crates/bg-parser/tests/upload_contract.rs` fails in CI otherwise (D-047). A parser change that adds report fields bumps `VALIDATOR_VERSION`; refused games are retried once when a newer validator answers. To see the live validator version: `POST` to `…/functions/v1/upload-game` with the publishable key as `apikey` and bearer gives `405 … "validator": N`.
- **Merging to `main` deploys** the site (Cloudflare Pages) and the Supabase migrations and functions (GitHub integration, D-031, D-036). After a merge that touches `supabase/`, the session (or you) checks: `/auth/v1/settings` says `disable_signup: true`, functions answer `401` without a token, the new function version answers.
- **The user's desktop app** runs from the main checkout's `target\release\desktop.exe`. After a merge that touches `crates/`: if `Hearthstone` is not running, `Stop-Process -Name desktop`, `cargo build --release --locked -p desktop -p tracker`, `Start-Process` it again (a build while it runs fails at the link step with "Acceso denegado"). If the parser revision changed: back up `%APPDATA%\TavernLedger\games.jsonl`, run `target\release\tavern-watch.exe --reparse --logs-dir C:\Battle.net\Battle.net\Hearthstone\Logs` with the app stopped, then start the app. After a build, `git checkout -- crates/desktop/gen/schemas` (the build rewrites them with CRLF only).
- **Cleanup:** before `git worktree remove`, check the worktree is clean and no process uses it (`Get-CimInstance Win32_Process` by command line): sessions leave dev servers behind (an `astro preview` on 4321, a `python -m http.server` on 8765 were found). Stop those first.
- **Hearthstone logs:** `C:\Battle.net\Battle.net\Hearthstone\Logs\Hearthstone_<date>\Power.log`; read it with shared access (`[IO.File]::Open(..., 'Read', 'ReadWrite')`) while the game runs. Print counts, tag names and card ids only, never names.
- A session's auto-mode may refuse an action (production writes, dashboard saves). Never do a refused action for it; tell the user. The hub's own browser saves on production settings may be refused too: then fill the form and ask the user to press Save.
- After the user's VPN or a network drop, sessions stop with "API Error: Connection lost": a `SendMessage` asking them to resume where they left off wakes them.
